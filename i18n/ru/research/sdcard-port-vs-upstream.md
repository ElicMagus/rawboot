# Порт SD/MMC-карты в `rawboot` против текущего `sdmmc.c` из upstream `szemzoa/awboot`

Исследовано: 2026. Цель: Allwinner T113-S3. Upstream закреплён на `szemzoa/awboot`
`main` HEAD `5380c00fc67c975433f25c57fb481aa2b91aebf8` (2025-11-21). Сравнивались файлы:
`arch/arm32/mach-t113s3/sdmmc.c`, `arch/arm32/mach-t113s3/sdmmc.h`, `board.c`,
`board.h` и `Makefile` [1]-[5]. Локальный код цитируется по символу, а не по строке (см.
`docs/agents/domain.md`).

Эта заметка — карточный аналог `research/sdhci-port-vs-upstream.md`; это
статический чек-лист parity для issue #20.

---

## 1. Краткое резюме

- Upstream `arch/arm32/mach-t113s3/sdmmc.c` на закреплённом SHA занимает 764 строки [1];
  `sdmmc.h` — 198 строк [2]. Последний upstream-коммит, затрагивающий драйвер, —
  `385481ffab` (2025-11-15, "refactor sdmmc driver, create library for fatfs, fdt,
  loaders").
- Наш loader загружается с SD-карты, тогда как закреплённый `board.h` для T113-S3 по
  умолчанию использует `CONFIG_BOOT_MMC=1` / `CONFIG_BOOT_SDCARD=0` [4]. Сборка
  upstream с `VARIANT=sdmmc` включает оба и сначала пробует SD, затем сбрасывает
  состояние и переходит к MMC [5]. Порт воспроизводит этот поток с приоритетом SD,
  поэтому живы обе ветви: SD-карта идёт по SD-пути, а MMC/eMMC-карта — по MMC-пути.
- Issue #19 уже заменил хостовый путь, работавший только через PIO, на upstream-разделение
  64-байтного IDMAC/PIO [6]. Issue #20 выравнивает карточный протокол поверх этого
  хостового API.
- `CONFIG_MMC_ENABLE_RSTN` по умолчанию равен `0` в `board.h` [4], поэтому опциональный
  аппаратный сброс eMMC через CMD6 не входит в закреплённое поведение T113-S3 и не
  воспроизводится.

### Вердикт

Поведение `sdmmc.c` в рамках задачи портировано: инициализация SD, инициализация MMC,
идентификация карты, разбор CID/CSD/EXT_CSD, расчёт ёмкости, переключение SD на 4 бита,
переключение MMC на high-speed/DDR/power-class/ширину шины и блочное чтение. Имена
следуют upstream (`sdmmc_*`, `MMC_*`, `SD_CMD_*`, `OCR_*`, `SD_VERSION_*`,
`MMC_VERSION_*`, `EXT_CSD_*`); типы и форма владения HCI остаются идиоматичными для Rust
согласно ADR-0007.

## 3. Расхождения, исправленные в #20

1. **Порядок инициализации SD.** Старый порт вызывал CMD0 и CMD8 в `sdmmc_detect`, а
   затем входил в `sd_send_op_cond`; upstream вызывает оба внутри `sd_send_op_cond`.
   Счётчик повторов был 100 вместо upstream-овых 50, и форма цикла отличалась. Заменено
   на upstream-последовательность CMD0/CMD8/CMD55/ACMD41 с постдекрементным бюджетом
   повторов.
2. **Инициализация MMC.** Старый порт отправлял лишний CMD1 с аргументом 0, использовал
   маски напряжения вместо upstream-овых OCR-аргументов на точное равенство и
   устанавливал `rca = 0`. Заменено на upstream-цикл CMD1 с 50 повторами, аргументы
   `0x40ff8000` / `0x40ff0080`, `MMC_VERSION_UNKNOWN` и `rca = 1`; откат при неудаче SD
   теперь сбрасывает контроллер и повторно отправляет CMD0 в точности как upstream.
3. **Семантика CSD/EXT_CSD.** Старый порт для неизвестного `EXT_CSD_REV` подставлял
   версию 0 и никогда не применял upstream-ово `tran_speed = 50 MHz` перед чтением
   EXT_CSD. Теперь обе части соответствуют upstream.
4. **Переключение скорости и ширины MMC.** Старая ветвь MMC отправляла CMD55 + CMD6 с
   «сырым» значением ширины. Порт теперь выполняет полную upstream-последовательность:
   проверка поддержки DDR, high-speed timing, запись HS_TIMING, power class для 4 бит,
   запись BUS_WIDTH, задержки 1 мс и общее итоговое обновление частоты/ширины.
5. **Ожидание статуса чтения.** Старое условие при переписывании оказалось
   инвертированным: оно завершало цикл, когда карта была ни TRAN, ни DATA. Теперь цикл
   идёт до TRAN или DATA, что соответствует upstream и позволяет `sdmmc_blk_read`
   вернуться.
6. **Имена.** Имена команд, ответов, статусов, OCR, флагов данных, версий и EXT_CSD
   теперь совпадают с upstream; `sdmmc_init`/`sdmmc_blk_read` заменяют старые методы
   `Sdcard_data::init`/`blk_read`.

## 4. Намеренные различия

- **Типы и владение.** `Sdcard`, `Sdcard_data`, `Sdhci` и `SdhciCmd` заменяют
  C-структуры; HCI принадлежит структуре данных, а не передаётся по ссылке, а точки
  входа чтения/инициализации возвращают `u64`/`i32` с аргументами `&mut`. Поведение и
  порядок полей остаются upstream-овыми (ADR-0007).
- **Логирование.** Upstream-овые `trace`/`debug`/`warning`/`error` становятся `print!`.
  Loader сохраняет свои лаконичные строки `SD/MMC card found` / `SD/MMC card not found`
  вместо upstream-овой `SHMC: ... card detected`; текст ошибок перенесён. Отладочные
  строки с версией EXT_CSD и ёмкостью в плавающей точке не печатаются.
- **Аппаратный сброс eMMC.** На закреплённой плате `CONFIG_MMC_ENABLE_RSTN` равен `0`,
  поэтому опциональный CMD6 RST_N и его отладочная строка намеренно отсутствуют.
- **Ветвь SPI.** `isspi` остаётся полем, и ветви SPI перенесены, но экземпляр платы
  T113-S3 не является SPI; ни один SPI-хост не создаётся.
- **Экземпляр платы eMMC.** Создаётся только `sdhci0`. eMMC на `sdhci2` выходит за рамки
  SD-функциональности T113-S3 и остаётся отложенным.
- **Тайм-аут сброса (#43).** `sdmmc_detect` прекращает попытку, когда `sdhci_reset`
  сообщает о тайм-ауте; upstream игнорирует результат сброса, потому что его сброс
  возвращается немедленно. Опросный сброс и последовательность инициализации CMD0 живут
  в `sdhci`; см. `research/sd-cold-start-brom.md`.
- **Транспортный сбой ACMD41 (#43).** `sd_send_op_cond` покидает цикл опроса только
  тогда, когда ACMD41 завершился успешно и установил бит занятости. Upstream тоже
  прерывает цикл при транспортном сбое и затем трактует устаревший ответ как OCR; здесь
  сбой расходует повтор внутри того же бюджета в 50 попыток, поэтому SD-путь
  отвергается до отката на MMC.
- **Нет хостового шва.** По решению родительской issue хостового теста для драйвера
  карты нет; parity проверяется этой статической таблицей плюс HIL на T113-S3.

## 5. Подтверждение на оборудовании

Проверено на T113-S3 с помощью `scripts/hil-check.sh target/rawboot-fel.bin iss20` из
ветви `feat/20-parity-sdcard` на коммите `0ae1ecc` (штамп образа `dirty=false`). UART всё
ещё нес предыдущий loader, поэтому прогон использовал документированный путь
`HIL_SKIP_PREFLIGHT=1`; скрипт слил его, сообщил один `Hello` и проверил требуемые
строки:

```
Hello
CLK: CPU PLL=PLL_CPU FREQ=1008MHz
CLK: PLL_peri (2X)=1200MHz, (1X)=600MHz, (800M)=800MHz
CLK: PLL_ddr=432MHz
trefi:7.8ms
DRAMC read ODT  off.
DRAM ODT value: 0x42.
DRAM simple test OK.
SD/MMC card found
SD: read 1 block(s), first bytes [00, 00, 00, 00]
S=0x4
PASS: UART assertions
```

- `SD/MMC card found` означает, что CMD0/CMD8/CMD55/ACMD41, CID/CSD/RCA/выбор карты и
  переключение на 50 МГц/4 бита прошли успешно по SD-пути.
- 512-байтное чтение превышает порог в 64 байта и потому идёт через IDMAC; блок заполнен
  нулями, так как тестовая карта пуста.
- Владелец подтвердил, что светодиод PD22 мигает в цикле payload.
