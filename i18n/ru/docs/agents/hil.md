# Аппаратная проверка в замкнутом контуре (HIL)

loader проверяется на реальном T113-S3. Эта страница — runbook: настройка хоста,
последовательность загрузки, захват UART и то, как читать результат. Скрипт из этого
репозитория — `scripts/hil-check.sh`; он автоматизирует шаги ниже.

## Запуски под управлением агента

Когда агент выполняет эти шаги, он задаёт один `question` на каждое физическое действие
(цикл питания, вставка карты, FEL/BOOT, подтверждение LED) и ждёт ответа, прежде чем
начать следующее действие. Он не объединяет несколько холодных стартов в один запрос.
В одном вызове `question` он показывает две вкладки: сам физический шаг и контрольный
«Уверен?» с вариантами «Да» и «Нет». Он действует, только если шаг подтверждён и выбрано
«Да»; иначе возвращается к вопросу о шаге. Это защищает от случайного нажатия. После
каждого прогона он сообщает PASS/FAIL, ключевые строки лога и следующий шаг.

## Плата и подключение

- SoC: Allwinner T113-S3, DDR3, 128 MiB.
- Отладочный UART: **USART0**, выводы **PE2/PE3**, **115200 8N1**. На хосте это CH340
  (`/dev/ttyUSB0`, переопределяется через `UART_DEV`).
- LED: **PD22**. loader переключает его каждые 50 мс в своём главном цикле; после handoff
  payload мигает вместо этого коротко-длинной последовательностью. Скрипт не видит LED,
  поэтому прогон заканчивается проверкой человеком.
- FEL: USB OTG в режиме FEL. Плата определяется как `1f3a:efe8` (некоторые адаптеры
  сообщают `1f3c:*`). BROM сэмплирует strap FEL только при **холодном включении питания**:
  полностью снимите питание, удерживайте FEL/BOOT, затем подайте питание. Удержание FEL
  через reset (или FEL+RESET) не пересэмплирует его, поэтому автоматизированный стенд
  должен переключать силовую линию, а не только `NRST`.

## Настройка хоста

1. Доступ к последовательному порту: добавьте пользователя в `dialout`
   (`sudo usermod -aG dialout "$USER"`, затем войдите снова). Оболочка, не подхватившая
   группу, всё ещё может выполнять захват через `sg dialout`.
2. Доступ к FEL: установите правило udev, чтобы `xfel` мог открывать устройство без root:
   ```sh
   echo 'SUBSYSTEM=="usb", ATTR{idVendor}=="1f3a", ATTR{idProduct}=="efe8", MODE="0666"' \
     | sudo tee /etc/udev/rules.d/99-sunxi-fel.rules
   sudo udevadm control --reload-rules && sudo udevadm trigger
   ```
   Добавьте второе правило для `idVendor=="1f3c"`, если ваша плата сообщает этот ID.
3. Инструменты: `xfel` (использовалась v1.4.0; здесь он лежит в `~/.local/bin/xfel`) и
   Python `pyserial` (`sudo apt install python3-serial` или `pip install pyserial`).
4. Проверка: `xfel version` должна печатать строку `T113`, пока плата находится в FEL.

## Загрузка и захват

`cargo xtask image` пишет два образа loader из одного и того же кода:
`target/rawboot-fel.bin`, слинкованный для SRAM по адресу `0x00028000`, и
`target/rawboot-boot-sd.bin`, слинкованный по адресу `0x00020000` для SD/SPI boot из
сектора 16 через BROM. Используйте FEL-образ с `hil-check.sh`; образ boot записывайте на
карту. loader сам инициализирует DRAM, поэтому `xfel ddr` **не** входит ни в одну из
процедур.

Соберите loader, затем запустите скрипт:

```sh
cargo xtask image
scripts/hil-check.sh target/rawboot-fel.bin hil
```

Для issue, в acceptance которого входит путь через карту, задайте `HIL_REQUIRE_SD=1`.
Тогда скрипт также требует строку `SD/MMC card found` и ненулевую строку
`SD: read N block(s)`. Оставляйте переменную незаданной, когда карта не вставлена. Для
issue, который должен доказать handoff, задайте ещё и `HIL_REQUIRE_HANDOFF=1`: тогда лог
должен содержать строку `BOOT: handoff to ...`, а цикл loader `S=0x` больше не
принимается. `HIL_REQUIRE_PAYLOAD=1` дополнительно сравнивает точку входа, адрес загрузки,
размер и контрольную сумму из handoff с `target/rawboot-payload.img` (`HIL_PAYLOAD_IMG`
переопределяет путь), поэтому устаревший `payload.bin` на карте проваливает проверку,
а не проходит её. `HIL_REQUIRE_LED=1` делает подтверждение LED человеком частью
результата: скрипт спрашивает на TTY или принимает `HIL_LED_CONFIRMED=1` в
неинтерактивных прогонах.

### Нестабильная инициализация SD

Холодные старты со вставленной картой могут завершаться ошибкой `SD/MMC card not found` (#43).
`scripts/hil-sd-retry.sh [image] [label]` повторяет `hil-check.sh` до
`HIL_SD_RETRIES` раз (по умолчанию 3) и повторяет только эту ошибку; сбои handoff,
payload и других проверок останавливают его сразу. Он принудительно задаёт
`HIL_SKIP_PREFLIGHT=1` и `HIL_NO_PROMPT=1`, потому что каждая повторная попытка заменяет
loader, оставшийся работать от предыдущей попытки. Задайте
`HIL_REQUIRE_LED=1 HIL_LED_CONFIRMED=1`, чтобы включить проверку LED, или запускайте
`hil-check.sh` напрямую, когда нужен чистый интерактивный прогон. Если FEL перестаёт
отвечать между попытками, переведите плату в FEL циклом питания и повторите.

Повторные попытки не обесточивают карту. Прежде чем считать сбой `cmd1`/ACMD41 дефектом
loader, выполните настоящий холодный старт, как описано ниже.

#### Холодный старт должен обесточивать карту (#43)

«Холодный» старт действительно проверяет драйвер только в том случае, если карта сама
теряет питание. На этом стенде USB-UART адаптер может подпитывать шину 3.3 V платы через
линии последовательного порта. Если адаптер оставлен подключённым, карта сохраняет своё
состояние после отключения питания через FEL; тогда холодные старты чередуют PASS/FAIL
даже на неизменённом `master`. Сбой выглядит как успешный CMD8, после которого ACMD41 так
и не выставляет бит busy, затем обычный переход к MMC по `cmd1 timeout`, и повторный
запуск loader без цикла питания платы это не исправляет.

Настоящий холодный старт:

1. Отключите USB-UART адаптер (и любой другой кабель, который может подпитывать
   плату), затем снимите питание с платы.
2. Подождите несколько секунд, чтобы шина питания карты разрядилась, вставьте карту,
   удерживайте FEL/BOOT, подайте питание и только потом снова подключите USB-UART
   адаптер.
3. Запустите `HIL_REQUIRE_SD=1 scripts/hil-check.sh target/rawboot-fel.bin cold<N>`.

Затем повторите два пути восстановления: вставьте карту после того, как плата оказалась
в FEL, и загрузите loader; и перезапустите loader через FEL, не снимая питание
(`HIL_SKIP_PREFLIGHT=1`). Наконец, выньте карту и убедитесь в `SD/MMC card not found` без
зависания и без бесконечного цикла повторных попыток.

Базовый `master @ 60e6867` прошёл 3/3 настоящих холодных старта таким образом, поэтому
сбой при отключённом адаптере указывает на loader или на карту, а не на стенд. Горячее
подключение после FEL и повторный запуск loader не обесточивают карту; они проверяют
восстановление с уже запитанной карты. Issue #43 закрыт как проблема процедуры стенда;
доказательства см. в `research/sd-cold-start-brom.md`.

### Образ payload на карте

loader читает `payload.bin` из FAT-раздела. Соберите мигающий payload, затем скопируйте
обёрнутый образ на смонтированную карту. Записать карту можно на любой машине с
кардридером; для HIL она должна быть только в плате, не на этом хосте:

```sh
cargo xtask payload
cp target/rawboot-payload.img /media/$USER/<partition>/payload.bin
```

Копируйте `target/rawboot-payload.img`, а не сырой
`target/armv7a-none-eabi/release/payload.bin`: у первого есть заголовок образа, который
разбирает loader. Если карта уже в плате, а плата в FEL, `cargo xtask fel-flash`
обновляет `payload.bin` и loader, не вынимая карту; см.
[FEL-прошивка карты на месте](#fel-flashing-the-card-in-place-42).

Необязательный `boot.cfg` рядом с `payload.bin` копируется в DRAM и предоставляется
payload как строка с завершающим NUL через `BootInfo.args` (до 4095 байт; окно в 4 KiB
включает терминатор). Без этого файла `BootInfo.args` равен нулю. Чтобы проверить handoff
сквозным образом, положите на карту известный файл и передайте его длину в байтах:

```sh
printf 'console=ttyS0' > /media/$USER/<partition>/boot.cfg   # 13 bytes
HIL_REQUIRE_SD=1 HIL_REQUIRE_HANDOFF=1 HIL_BOOT_CFG_LEN=13 \
    scripts/hil-check.sh target/rawboot-fel.bin bootcfg
```

`HIL_BOOT_CFG_LEN` заставляет скрипт требовать строку `ARGS: boot.cfg <len> bytes at 0x...`
и тот же указатель в поле `args 0x...` из handoff. Нечитаемый или не помещающийся файл
прерывает загрузку с `BOOT: boot.cfg: ...`, вместо того чтобы загружаться с молча
обрезанными аргументами.

Для полного сквозного acceptance (SD -> FAT -> DRAM -> handoff -> мигание) запускайте со
всеми проверками:

```sh
HIL_REQUIRE_SD=1 HIL_REQUIRE_HANDOFF=1 HIL_REQUIRE_PAYLOAD=1 HIL_REQUIRE_LED=1 \
    scripts/hil-check.sh target/rawboot-fel.bin blink
```

### FEL payload (без SD-карты)

`HIL_FEL_PAYLOAD=1` загружает `target/rawboot-payload.img` в SRAM и записывает почтовый
ящик FEL, чтобы loader загрузил его без SD-карты. Почтовый ящик соответствует
`rawboot-image/src/fel.rs`:

| слово | адрес       | значение                                   |
| ----- | ----------- | ------------------------------------------ |
| 0     | `0x00044000` | магия `0x4d464252` (`RBFM` little-endian)  |
| 1     | `0x00044004` | адрес образа payload (`0x00039000`)        |
| 2     | `0x00044008` | размер образа payload в байтах             |
| 3     | `0x0004400c` | адрес строки аргументов или ноль           |

Окно образа — `0x00039000..0x00044000` (44 KiB); необязательные аргументы располагаются
по `0x00038000`. Этот путь намеренно обходит `xfel ddr` (issue #23) и пропускает
инициализацию SD. Запускайте его с проверками handoff и LED:

```sh
cargo xtask image
cargo xtask payload
HIL_FEL_PAYLOAD=1 HIL_REQUIRE_LED=1 scripts/hil-check.sh target/rawboot-fel.bin fel
```

`HIL_FEL_ARGS="..."` передаёт строку аргументов с завершающим NUL через почтовый ящик по
адресу `0x00038000` (не более 4 KiB, включая терминатор); прогон проверяет указатель,
который сообщает loader. Проверка payload на этом пути выполняется автоматически, а
`HIL_REQUIRE_SD` отклоняется, потому что доступа к SD не происходит.

### SD/SPI boot (без FEL)

BROM загружает образ boot из сектора 16 сразу по адресу `0x00020000`, тогда как FEL-образ
слинкован по `0x00028000` и записывается через `xfel`. Кладите на карту
**`target/rawboot-boot-sd.bin`**: FEL-образ в секторе 16 работает со смещением 32 KiB и
умирает до UART, оставляя плату молчащей с ровно горящим LED.

Карте нужен FAT-раздел (этот runbook предполагает LBA 2048, как в bring-up #37) и
`payload.bin` (или `boot.cfg`) в корне. `cargo xtask sd-image` собирает SD boot prefix:
MBR, указывающий на этот раздел, плюс `target/rawboot-boot-sd.bin` в секторе 16, по
умолчанию ровно 2048 секторов (1 MiB). Он ничего не форматирует и не копирует payload; и
то и другое остаётся на разделе.

Соберите и запишите prefix поверх карты, на которой уже есть FAT-раздел по LBA 2048:

```sh
cargo xtask image
cargo xtask payload
cargo xtask sd-image --partition-sectors 1843200
sudo dd if=target/rawboot-sd-mbr.img of=/dev/sdX bs=512 conv=notrunc,fsync
cp target/rawboot-payload.img /media/$USER/<partition>/payload.bin
```

`--partition-sectors` должен быть фактическим размером раздела в секторах (узнайте его
из `fdisk -l /dev/sdX`); `--start-lba` по умолчанию равен 2048 и меняет как длину prefix,
так и запись в MBR; `--loader` переопределяет значение по умолчанию
`target/rawboot-boot-sd.bin`. Prefix не содержит ни FAT-тома, ни payload: форматирование
всего устройства (`mkfs.vfat /dev/sdX`) или запись поверх него полного образа диска
уничтожает loader в секторе 16. Форматируйте и копируйте только раздел
(`mkfs.vfat /dev/sdX1`, смонтируйте его, скопируйте `payload.bin`) либо повторите `dd`
prefix после этого.

Обёртка `scripts/flash-sd.sh` выполняет шаги выше, определяет начало и размер раздела и
отказывается от смонтированного устройства, карты с GPT/несколькими разделами или карты,
на которой находится `/`. Без `--device` она выбирает единственный съёмный/USB/MMC диск
и спрашивает, когда их несколько; `--list` показывает их. Запускайте её от своего
пользователя, не через `sudo`: она повышает права только для `dd`, `mkfs` и `mount`,
поэтому `target/` остаётся принадлежащим пользователю при работе cargo.

```sh
# see which cards/disks the script can pick
scripts/flash-sd.sh --list
# update the loader; keep the partition and its payload
scripts/flash-sd.sh --copy-payload
# recreate the partition as FAT32 (destroys its contents), then copy the payload
scripts/flash-sd.sh --device /dev/sdX --format --yes
```

`--dry-run` только печатает план; `--skip-build` переиспользует существующие образы;
`--partition`, `--start-lba`, `--partition-sectors`, `--loader`, `--payload`,
`--boot-cfg` и `--payload-name` переопределяют автоопределение и значения по умолчанию.
Те же значения могут приходить из `SD_DEV`, `SD_PART`, `START_LBA`, `PARTITION_SECTORS`,
`LOADER_IMG`, `PAYLOAD_IMG`, `BOOT_CFG`, `FORMAT_PARTITION` и `COPY_PAYLOAD`. Скрипт
спрашивает перед каждым разрушительным действием, если не передан `--yes` (пример
`--format --yes` пропускает оба запроса), отклоняет `rawboot-fel.bin` в секторе 16,
требует, чтобы раздел уже был FAT, если не задан `--format`, и форматирует только раздел,
никогда не весь диск.

Захватите прогон самозагрузки, запустив захват **до** цикла питания, затем подайте питание
(strap BROM сэмплируется при холодном включении питания; см.
[Захват самозагружающейся платы](#capture-a-self-booting-board-no-fel)):

```sh
setsid sg dialout -c 'python3 scripts/hil_serial.py /tmp/boot.log --seconds 10 \
    --require-handoff --payload target/rawboot-payload.img' &
```

Прогон проходит, когда лог доходит до `BOOT: handoff to ...` и PD22 затем показывает
коротко-длинную последовательность payload (120 мс включено, 180 мс выключено, 600 мс
включено, 900 мс выключено). Ровное переключение каждые 50 мс означает, что loader всё
ещё в своём цикле `S=0x`; тишина указывает на неверный образ в секторе 16.

Запускайте HIL из ветки кода, которая проверяется. Инструкции по проверке и обновления
runbook можно коммитить до прогона; записывайте PASS только после его успеха.
`cargo xtask image` пишет `target/rawboot-fel.bin.build` и
`target/rawboot-boot-sd.bin.build` с исходным коммитом, веткой и флагом dirty;
`hil-check.sh` отклоняет FEL-образ, коммит которого не совпадает с `HEAD`, поэтому
пересобирайте после переключения веток (`HIL_SKIP_PROVENANCE=1` — аварийный выход).

Переведите плату в FEL холодным циклом питания (выключите питание, удерживайте FEL/BOOT,
включите питание), а не через `xfel reset` или обычный reset: strap сэмплируется только
при включении питания, а `xfel reset` сбрасывает через watchdog, который остаётся
взведённым, поэтому loader затем загружается в цикле. loader, оставшийся работать от
предыдущего прогона, тоже продолжает печатать на USART0, поэтому очистите его циклом
питания перед каждым прогоном. В терминале скрипт печатает это и ждёт Enter; прогоны
через pipe или с `HIL_NO_PROMPT=1` пропускают запрос.

Успешный `xfel version` **не** доказывает, что плата простаивает в FEL: USB-гаджет FEL
может по-прежнему отвечать, пока loader от предыдущего прогона печатает на USART0.
Авторитет — предварительная проверка тишины UART в скрипте.

Если loader от предыдущего прогона всё ещё печатает, `HIL_SKIP_PREFLIGHT=1` сливает
USART0 и заменяет его образом под тестом. Предупреждение предполётной проверки тогда
ожидаемо: старые строки `S=` — это устаревший вывод, а не цикл сброса. Захват по той же
причине отбрасывает проверку цикла сброса, поэтому устаревшие строки `Hello` и фрагменты,
которые он ловит, пока старый loader заменяется, больше не проваливают прогон; все
остальные проверки по-прежнему действуют, поэтому действительно отсутствующая строка
загрузки всё равно будет обнаружена. Используйте это вместо повторных циклов питания,
когда `xfel` ещё отвечает; используйте цикл питания, когда не отвечает.

Скрипт:

1. сверяет метку сборки образа с `HEAD`;
2. ждёт до 3 минут отзывчивого FEL (`xfel version` успешен);
3. требует, чтобы UART был тих в течение короткого окна, чтобы всё ещё работающий loader
   был обнаружен как занятая плата, а не выглядел позже как цикл сброса
   (`HIL_SKIP_PREFLIGHT=1` понижает эту проверку до предупреждения);
4. сливает входной буфер UART перед загрузкой;
5. пишет образ по `0x00028000` и переходит на него; с `HIL_FEL_PAYLOAD=1` он также пишет
   образ payload и почтовый ящик в SRAM перед переходом;
6. захватывает USART0 на несколько секунд, печатает уникальные строки и проверяет `Hello`,
   `CLK:`, `DRAM simple test OK` и либо цикл loader (`S=0x`), либо handoff payload
   (`BOOT: handoff to ...`); с `HIL_REQUIRE_SD=1` он также проверяет `SD/MMC card found` и
   ненулевую `SD: read N block(s)`, с `HIL_FEL_PAYLOAD=1` требует строку `FEL: payload`,
   с `HIL_REQUIRE_HANDOFF=1` требует строку handoff, а с `HIL_REQUIRE_PAYLOAD=1`
   (или `HIL_FEL_PAYLOAD=1`) требует, чтобы handoff совпадал с хостовым образом payload.
   Он завершается ошибкой, когда появляется больше одного `Hello` (цикл сброса или
   устаревший захват); с `HIL_SKIP_PREFLIGHT=1` эта проверка отбрасывается, поэтому вывод,
   оставленный заменённым loader, игнорируется;
7. с `HIL_REQUIRE_LED=1` просит человека подтвердить, что PD22 показывает коротко-длинную
   последовательность payload (120 мс включено, 180 мс выключено, 600 мс включено, 900 мс
   выключено, повторяется), а не ровное переключение loader каждые 50 мс; на интерактивном
   TTY (если не задан `HIL_NO_PROMPT=1`) он читает ответ, иначе требует
   `HIL_LED_CONFIRMED=1`. Без этого флага он только печатает запрос ручной проверки.

Сырой захват сохраняется в `/tmp/rawboot-hil-<label>.log`.

### Ручная загрузка (без скрипта)

```sh
xfel write 0x00028000 target/rawboot-fel.bin
xfel exec 0x00028000
```

Для ручной загрузки FEL payload запишите образ и почтовый ящик перед переходом:

```sh
size=$(stat -c %s target/rawboot-payload.img)
xfel write 0x00028000 target/rawboot-fel.bin
xfel write 0x00039000 target/rawboot-payload.img
xfel write32 0x00044004 0x00039000
xfel write32 0x00044008 "$size"
xfel write32 0x0004400c 0
xfel write32 0x00044000 0x4d464252
xfel exec 0x00028000
```

Не выполняйте сначала `xfel ddr t113-s3`. Он инициализирует DRAM, и вторая инициализация
в loader зависает на PLL_DDR (issue #23). loader нуждается только в SRAM, пока сам не
инициализирует DRAM.

Если UART захватывается вручную, слейте его перед `xfel exec` (например,
`python3 -c 'import serial; s=serial.Serial("/dev/ttyUSB0",115200); s.reset_input_buffer()'`)
и захватывайте на 115200 8N1.

### Встроенный транспорт FEL (без `xfel`)

`cargo fel` говорит напрямую по протоколу FEL BROM; ему нужно правило udev выше, но не
внешний `xfel`. Это сквозным образом проверяет issue #40:

```sh
cargo xtask image
cargo fel version        # must print `SoC:        T113-S3 (chip id 0x1859)`
```

Запишите шаблон в SRAM и прочитайте его обратно (чтение печатает hex-дамп; `--output`
сохраняет байты для `cmp`):

```sh
size=$(stat -c %s target/rawboot-payload.img)
cargo fel write 0x00039000 target/rawboot-payload.img
cargo fel read 0x00039000 "$size" --output /tmp/rawboot-readback.img
cmp target/rawboot-payload.img /tmp/rawboot-readback.img
```

Для exec загрузите stub, который возвращает управление в BROM (`bx lr`), запустите его,
затем снова прочитайте память:

```sh
printf '\x1e\xff\x2f\xe1' > /tmp/rawboot-return.bin   # bx lr
cargo fel write 0x00030000 /tmp/rawboot-return.bin
cargo fel exec 0x00030000
cargo fel read 0x00030000 4
```

`cargo fel exec` возвращает управление только когда stub отдаёт его обратно BROM; stub,
который не возвращается, заканчивается таймаутом передачи. `scripts/hil-check.sh` всё ещё
использует `xfel`; этот CLI предназначен для ручных проверок выше.

### DDR-init stub и flasher (без SD)

Issue #41 разделяет путь FEL на возвращающийся DDR-init stub и слинкованный в DRAM
flasher; issue #42 добавляет задачу SD/FAT (см. следующий раздел). Соберите оба образа и
проведите весь эксперимент встроенным транспортом:

```sh
cargo xtask flasher
cargo fel bringup target/rawboot-ddr.bin target/rawboot-flasher.bin
```

`bringup` определяет SoC, пишет stub по `0x00028000`, выполняет его и читает его результат
в SRAM (`0x0002d000`: магия `RBDD`, затем размер DRAM в MiB), пишет и читает обратно
шаблон по `0x40002000`, затем размещает задачу `NOOP` по `0x40000000`, flasher по
`0x40010000`, выполняет его и читает статус по `0x40000100`. Ожидаемый хвост:

```
DRAM:       128 MiB
pattern:    OK at 0x40002000
status:     sequence 1, step 2 (done), result 0 (ok)
```

Адреса и раскладка `FlashJob`/`FlashStatus` находятся в `rawboot-image/src/flash.rs`
(ADR-0013); CLI печатает те же значения. Этот путь намеренно **не** использует
`xfel ddr`: именно stub инициализирует DRAM.

- Если stub не возвращается, `bringup` блокируется на следующем чтении FEL до таймаута
  транспорта, и плата перестаёт отвечать FEL. Зафиксируйте сбойный шаг и верните #41 в
  triage; не повторяйте `xfel ddr` как обходной путь.
- `DDR-init stub did not report success` означает, что `exec` вернулся, но результат в
  SRAM отсутствует или драйвер вернул размер `0`; плата всё ещё пригодна, повторите после
  проверки лога.
- `DRAM read-back ... returned ...` называет первое несовпавшее слово. Не переходите к
  flasher; окно DRAM недостоверно.
- Статус с `result` не `0 (ok)` — всё ещё успешный круговой обмен, но задача провалилась;
  CLI завершается с ненулевым кодом, напечатав шаг и результат.

stub и flasher не несут заголовок eGON и не взаимозаменяемы с образами loader.

### FEL-прошивка карты на месте (#42)

Карта остаётся в плате. Переведите плату в FEL холодным циклом питания, оставьте карту
вставленной и запустите:

```sh
cargo xtask fel-flash --yes
```

`--dry-run` выполняет ту же сборку и проверку, печатает план и выходит, не открывая FEL и
не касаясь карты; используйте его для проверки артефактов и путей. Для фактической записи
нужен `--yes`.

Без `--skip-build` команда сначала запускает `cargo xtask image`, `payload` и `flasher`,
затем читает `target/rawboot-boot-sd.bin`, `target/rawboot-payload.img`,
`target/rawboot-ddr.bin` и `target/rawboot-flasher.bin`. Она проверяет, что loader — это
запечатанный SD/SPI-образ, и отклоняет FEL-вариант (`rawboot-fel.bin`, метка сборки
`variant=fel` или совпадающие байты), разбирает образ payload и ограничивает `boot.cfg`
4095 байтами. Затем она определяет T113-S3, запускает DDR-init stub, проверяет DRAM
шаблоном, размещает план прошивки и три области в DRAM и выполняет flasher. flasher
инициализирует USART0 и печатает туда диагностику драйверов SD/FAT, поэтому сбойный шаг
CMD24 или FAT виден как в логе UART, так и в статусе.

Параметры:

- `--payload <path>` — образ payload (по умолчанию `target/rawboot-payload.img`); это
  должен быть обёрнутый образ, а не сырой `payload.bin`.
- `--boot-cfg <path>` — также записать этот файл как `boot.cfg`; без него существующий
  `boot.cfg` остаётся нетронутым.
- `--loader <path>`, `--flasher <path>`, `--ddr-stub <path>` — переопределяют собранные
  образы.
- `--sequence <n>` — последовательность job/status (по умолчанию 1).
- `--skip-build` — переиспользовать образы, уже находящиеся в `target/`; пересобирайте
  после переключения веток.
- `--dry-run` — собрать/проверить и напечатать план; никогда не открывать FEL.
- `--yes` — требуется для фактической записи; без него команда проверяет и
  останавливается.

`scripts/hil-flash.sh` оборачивает захват: он запускает логгер UART, выполняет
`cargo xtask fel-flash --yes`, печатает вывод хоста и хвост UART и требует
`step 2 (done), result 0 (ok)`. Он не выполняет цикл питания; сначала сделайте холодный
старт платы.

Что flasher проверяет и пишет:

1. MBR имеет сигнатуру `55 AA` и запись таблицы разделов FAT; отклоняются чистый
   FAT-том без MBR, MBR без FAT-записи и раздел, начинающийся в секторе 16 или раньше;
2. loader в секторе 16 заканчивается до раздела, а раздел лежит внутри карты;
3. `payload.bin` (и `boot.cfg`, если передан) заменяется в корне FAT и читается обратно;
4. только затем запечатанный loader записывается в сектор 16 и читается обратно;
5. сектор 0 никогда не пишется; flasher перечитывает MBR и сообщает `MBR changed`, если
   он отличается.

Ожидаемый хвост при успехе:

```
SoC:        T113-S3
DRAM:       128 MiB
staged:     payload N bytes, boot.cfg 0 bytes, loader N bytes
status:     sequence 1, step 2 (done), result 0 (ok)
card:       payload files and loader written; MBR unchanged
```

**DDR-init и повторные попытки.** stub не идемпотентен: каждый запуск снова вызывает
`DramPara::init_dram()` и ждёт захвата PLL_DDR, поэтому повтор может зависнуть так же, как
`xfel ddr` перед loader. Это другое условие, нежели #23, который конкретно про внешний
`xfel ddr`, запущенный перед loader. HIL #52 измерил условия повторов: три запуска
`bringup` за один цикл питания, второй `fel-flash` после успешного и повторный запуск
после ошибки SD — все вернулись в BROM и завершились с `step 2 (done), result 0 (ok)`.
Однако более поздний повтор завис: после успешного `raw-write-test` за один цикл питания
следующий `fel-flash` истёк по таймауту, ожидая возврата DDR stub. Устройство всё ещё
определялось по USB, но `cargo fel version` не отвечал, и плате требовался холодный
старт. Поэтому повторный stub — не проверенный путь: запускайте один stub на одно
холодное включение и делайте цикл питания перед повторной попыткой.

| Условие | Процедура | Ожидается | Наблюдалось |
| --- | --- | --- | --- |
| Холодный старт, один `bringup` | цикл питания в FEL, запуск `cargo fel bringup target/rawboot-ddr.bin target/rawboot-flasher.bin` | `DRAM: 128 MiB`, `pattern: OK at 0x40002000`, `status: sequence 1, step 2 (done), result 0 (ok)` | PASS, HIL #52 |
| Три `bringup` за один цикл питания | запустить `bringup` три раза, не снимая питание | три одинаковых успеха | PASS, HIL #46; повторно подтверждено на HIL #52 |
| Повторный `fel-flash` после успешного `fel-flash` | запустить `cargo xtask fel-flash --yes` дважды за один цикл питания | второй запуск сообщает `step 2 (done), result 0 (ok)` | PASS один раз на HIL #52 (после переустановки карты в FEL); более поздний повтор завис, поэтому не полагайтесь на это |
| Повторный `fel-flash` после ошибки SD | заставить flasher сбойнуть до статуса (вынуть карту или использовать раздел, начинающийся в секторе 16 или внутри него), затем повторить `fel-flash --yes` за тот же цикл питания | второй запуск сообщает чистый статус | PASS один раз на HIL #52 (первый запуск `SD card offline`, второй успешен); более поздний повтор завис |
| Четыре холодных старта, адаптер подключён, загрузочная карта | сделать цикл питания четыре раза, не отключая адаптер и не вынимая карту | DDR-init успешен всякий раз, когда достигается FEL; BROM может загрузиться с карты вместо FEL | HIL #52: FEL достигнут 4/4; DDR 4/4 PASS; карта `found` 1/4, `SD card offline` 3/4 |
| Четыре холодных старта, адаптер подключён, сектор 16 инвалидирован | один раз запустить `cargo xtask raw-write-test --yes`, затем сделать цикл питания четыре раза, не отключая адаптер и не вынимая карту | FEL детерминирован; DDR-init успешен каждый раз; SD может чередоваться (#43) | HIL #52: DDR 4/4 PASS; SD на нечётных стартах FAIL (2/2), на чётных PASS (2/2) |

Записывайте результат в таблицу только после того, как владелец подтвердит его на стенде;
не помечайте неизмеренную строку как PASS. Повторяйте строку холодного старта после любого
изменения платы или карты.

**Холодные старты с подключённым адаптером.** Оставленный подключённым USB-UART адаптер
подпитывает плату, поэтому карта не обесточивается по-настоящему, а карта с загрузочным
loader в секторе 16 может ещё и заставить BROM загрузиться с SD вместо входа в FEL. На
HIL #52 с загрузочной картой только один из четырёх таких стартов обнаружил карту; старт,
который не отвечает `cargo fel version`, загрузился с карты, а не провалил DDR-init.
Проверяйте `cargo fel version` перед началом строки матрицы.

Чтобы измерить чередование карты без кражи загрузки BROM, сначала инвалидируйте сектор 16:
`cargo xtask raw-write-test --yes` пишет туда тестовый блок `RBRW`, оставляет сектор 0 и
FAT-раздел нетронутыми и делает FEL детерминированным. С такой картой HIL #52 увидел
четыре холодных старта с подключённым адаптером: DDR-init прошёл 4/4, а чередование SD
было строгим (нечётные старты `SD card offline`, чётные — `done`/`ok`). После этого
восстановите loader через `fel-flash`. Это чередование — #43 (состояние питания карты), а
не результат DDR-init. Отключайте адаптер перед снятием питания для настоящего холодного
старта и вынимайте карту, когда вход в FEL должен быть детерминированным.

flasher сообщает сбойный шаг и причину в статусе, а `fel-flash` печатает их перед выходом
с ненулевым кодом. Частые случаи:

- `SD init: SD card offline` — нет карты, карта не определилась или проблема стенда #43;
  вставьте карту и холодным стартом переведите плату в FEL.
- `read MBR: read failed` — не удалось прочитать первый блок карты; считайте карту
  офлайн и повторите после холодного старта.
- `layout: no MBR` / `layout: no FAT partition` — карта не подготовлена; `fel-flash` не
  форматирует и не создаёт раздел. Сначала подготовьте её (вне рамок), затем повторите.
- `layout: unsafe card layout` — FAT-раздел начинается в секторе 16 или внутри него, либо
  loader заходил бы в него.
- `layout: card too small` — раздел MBR или loader не помещается на карту.
- `write payload` / `write boot.cfg` `create file failed`, `truncate failed`, `file write
  failed` или `file flush failed` — карта не приняла запись FAT; MBR и раздел остаются на
  месте, но не доверяйте обновлённым файлам, пока не пройдёт повторный запуск. На стендовой
  карте SDSC это было #47, исправлено в PR #49; если повторится, считайте это новым
  дефектом пути записи, а не проблемой DDR-init.
- `write loader` `write failed` — запись сектора 16 не удалась; старый loader может всё ещё
  быть там, но не загружайтесь с карты, пока не пройдёт повторный запуск.
- `verify FAT files` / `verify loader` `read-back mismatch` — карта вернула не то, что было
  записано; повторите, а если не проходит — замените карту.
- `verify loader` `MBR changed` — остановитесь и не загружайтесь с этой карты; осмотрите её.
- `plan: bad plan or staged image` — размещённый план/loader/payload не прошёл проверку;
  пересоберите с `cargo xtask image`/`payload`/`flasher` и повторите (без `--skip-build`).
- `USB device disconnected` или таймаут FEL до статуса — stub или flasher не вернулся в
  BROM. Переведите плату в FEL холодным циклом питания и повторите; не откатывайтесь к
  `xfel ddr`. Предпочитайте свежий холодный старт повторному запуску stub за тот же цикл
  питания, который таблица выше оставляет неизмеренным.

После успешного прогона снимите strap FEL и выполните холодную загрузку с карты.
Захватите её через `hil_serial.py` (запускайте захват до подачи питания, как в
[Захват самозагружающейся платы](#capture-a-self-booting-board-no-fel)) и проверьте
handoff:

```sh
setsid sg dialout -c 'python3 scripts/hil_serial.py /tmp/boot.log --seconds 10 \
    --require-handoff --payload target/rawboot-payload.img' &
```

Путь через карту проходит, когда лог показывает `SD/MMC card found`, `FAT: mounted` и
`BOOT: handoff to ...`, а PD22 затем показывает коротко-длинную последовательность
payload. Ровное переключение каждые 50 мс означает, что loader всё ещё в своём цикле
`S=0x`; тишина указывает на неверный образ в секторе 16. Для полного прогона HIL со всеми
проверками используйте процедуру холодного старта выше с
`HIL_REQUIRE_SD=1 HIL_REQUIRE_HANDOFF=1 HIL_REQUIRE_PAYLOAD=1 HIL_REQUIRE_LED=1`.

### Сырая диагностика записи SD (без MBR/FAT)

Когда запись на карту не удаётся, а чтение работает, отделите путь блочной записи от
состояния FAT и раздела холодным стартом в FEL и командой:

```sh
cargo xtask raw-write-test --yes
```

Она запускает DDR-init stub, пишет известный 512-байтовый блок в LBA 16, читает его
обратно и печатает шаг/результат. Она требует `--yes` и перезаписывает сектор 16
(SD-загрузчик на подготовленной карте); сектор 0 никогда не пишется. Успешный прогон
заканчивается:

```
status:     sequence 1, step 2 (done), result 0 (ok)
raw test:   sector 16 written and read back identical
```

Запись, сообщающая `step 12 (raw write), result 9 (write failed)`, означает, что драйвер
не смог завершить CMD24; `step 13 (raw verify)` отделяет сбой чтения обратно от сбоя
записи.

### Захват самозагружающейся платы (без FEL)

Когда плата загружается сама — с SD или SPI, без шага `xfel` — запускайте захват **до**
цикла питания и позвольте `hil_serial.py` оценить его. Он сливает порт в течение одной
секунды (`--drain`) и отбрасывает прочитанное, поэтому подавайте питание только после
этого окна. Затем он записывает лог с метками времени и печатает уникальные строки плюс
результаты проверок:

```sh
setsid sg dialout -c 'python3 scripts/hil_serial.py /tmp/boot.log --seconds 10 \
    --require-handoff --payload target/rawboot-payload.img' &
```

`sg dialout` нужен только тогда, когда оболочка не подхватила группу `dialout`. Сырой лог
быстро растёт на занятой плате (может достигать мегабайт); читайте сводку
`hil_serial.py`, а не вываливайте файл.

## Ожидаемый лог

Текущий `master` печатает (с вставленной картой, без валидного `payload.bin`):

```
Hello
CLK: CPU PLL=PLL_CPU FREQ=1008MHz
CLK: PLL_peri (2X)=1200MHz, (1X)=600MHz, (800M)=800MHz
CLK: PLL_ddr=432MHz
trefi:7.8ms
DRAMC read ODT  off.
DRAM ODT value: 0x42.
DRAM simple test OK.
SD/MMC card found
SD: read 1 block(s), first bytes [00, 00, 00, 00]
S=0x4
```

С валидным `payload.bin` loader печатает строки монтирования и handoff вместо входа в свой
цикл:

```
FAT: mounted Fat32 at LBA 0 (987758592 bytes)
ARGS: no boot.cfg
BOOT: handoff to 0x42000000: 192 bytes at 0x42000000, checksum 0x17e889cb, BootInfo 0x47feffe0, SP 0x48000000, args 0x00000000
```

С `boot.cfg` на карте строка аргументов называет файл и его адрес в DRAM, а handoff несёт
тот же указатель:

```
FAT: mounted Fat32 at LBA 0 (987758592 bytes)
ARGS: boot.cfg 13 bytes at 0x47ffefd0
BOOT: handoff to 0x42000000: 192 bytes at 0x42000000, checksum 0x17e889cb, BootInfo 0x47feffe0, SP 0x48000000, args 0x47ffefd0
```

С `HIL_FEL_PAYLOAD=1` он пропускает инициализацию SD и печатает вместо этого запрос из
почтового ящика:

```
FEL: payload image 0x00039000, 192 bytes, args 0x00000000
BOOT: handoff to 0x42000000: 192 bytes at 0x42000000, checksum 0x17e889cb, BootInfo 0x47feffe0, SP 0x48000000, args 0x00000000
```

После handoff UART молчит, если payload не печатает, поэтому захват заканчивается после
строки `BOOT: handoff to`. Затем payload мигает PD22: 120 мс включено, 180 мс выключено,
600 мс включено, 900 мс выключено, повторяется. Собственный цикл loader переключает каждые
50 мс, поэтому последовательность отличает завершённый handoff от loader, который так и не
вышел из своего цикла. Адреса, размер payload и контрольная сумма зависят от заголовка
образа и обнаруженного размера DRAM.

- `CLK: PLL_ddr` читается до `dram.init()`, поэтому показывает значение до DRAM;
  следующая за этим инициализация DRAM устанавливает 792 MHz. См.
  `research/clk-port-vs-upstream.md`.
- `SD/MMC card found` и строка `SD: read ...` доказывают работу пути SDHCI/IDMAC. Первые
  байты — это то, что содержит блок 0; пустая тестовая карта возвращает нули. С
  `HIL_REQUIRE_SD=1` эти две строки становятся проверками.
- `BOOT: handoff to ...` печатается после размещения payload, проверки его контрольной
  суммы по месту назначения и записи `BootInfo`. `HIL_REQUIRE_HANDOFF=1` делает её
  обязательной; `HIL_REQUIRE_PAYLOAD=1` также сверяет её точку входа, адрес загрузки,
  размер и контрольную сумму с `target/rawboot-payload.img`. Её поле `args` — это указатель
  на `boot.cfg` или ноль.
- `ARGS: boot.cfg ...` (путь SD) доказывает, что loader прочитал необязательный файл и
  зарезервировал копию с завершающим NUL; `ARGS: no boot.cfg` означает, что payload
  получает `args = 0`. loader не разбирает файл: его смысл принадлежит payload.
- `FEL: payload ...` доказывает, что loader прочитал почтовый ящик FEL и выбрал
  загруженный образ. `HIL_FEL_PAYLOAD=1` делает её обязательной и печатает указатель на
  аргументы из почтового ящика (`args 0x...`); путь SD сообщает то же поле в строке handoff
  и через `ARGS:`.
- `SD/MMC card not found` ожидается, когда карта не вставлена. Это не отменяет проверки
  часов и DRAM. Полный parity SD/MMC карт (#20) рассматривается в
  `research/sdcard-port-vs-upstream.md`.
- `S=0x...` повторяется, пока работает собственный цикл LED loader, с переключением каждые
  50 мс. Скрипт останавливается через несколько секунд. Карта с валидным `payload.bin`
  вместо этого выполняет handoff, печатает `BOOT: handoff to ...` и мигает коротко-длинной
  последовательностью payload.

## Устранение неполадок

- `xfel` сообщает `No FEL device found`: плата не в FEL, или USB-кабель только для данных
  и не подключён к порту OTG/FEL. Снова войдите в FEL и выполните цикл питания.
- `xfel` сообщает `Can't connect to device`: узел устройства недоступен для записи
  пользователю. Проверьте правило udev и `ls -l /dev/bus/usb/<bus>/<dev>`.
- Предполётная проверка сообщает `UART is not quiet`: loader от предыдущего прогона всё ещё
  печатает (или линия «плавает»), даже если `xfel version` отвечает. Повторите с
  `HIL_SKIP_PREFLIGHT=1`, чтобы слить его и заменить loader, либо переведите плату в FEL
  циклом питания (не `xfel reset`) и повторите.
- `image commit ... does not match HEAD`: образ старше переключения ветки или коммита.
  Пересоберите через `cargo xtask image` в ветке под тестом.
- `... is linked at 0x..., expected 0x...`: loader был слинкован с неверным скриптом.
  `cargo xtask image` собирает оба варианта и падает здесь, вместо того чтобы выпустить
  незагружаемый образ; проверьте `rawboot/build.rs` и `rawboot-rt/link*.x`.
- Холодное включение питания с SD молчит, а PD22 горит ровно: в секторе 16 лежит
  FEL-образ (`0x00028000`) вместо `target/rawboot-boot-sd.bin` (`0x00020000`). Два образа
  не взаимозаменяемы; пересоберите и перезапишите prefix через `cargo xtask image` и
  `cargo xtask sd-image --partition-sectors <n>`, затем `dd ... conv=notrunc`.
- HIL падает с `missing SD/MMC card found` или `missing a successful SD read`: нет карты,
  карта нечитаема или `HIL_REQUIRE_SD=1` задан без карты. Вставьте карту и повторите либо
  снимите флаг для теста без карты.
- `SMHC: cmd1 timeout (rint=0x00000100, flag=0x00000004)`, за которым следует `SD/MMC card
  not found` при холодном включении питания с уже вставленной картой: CMD1 — это переход
  к MMC, значит путь SD уже провалился (CMD8 или ACMD41). Сначала проверьте, что карта
  действительно теряла питание: оставленный подключённым USB-UART адаптер может
  подпитывать плату и сохранять состояние карты, из-за чего холодные старты чередуют
  PASS/FAIL на неизменённом `master` (issue #43). Отключите адаптер, пока плата выключена,
  затем повторите процедуру настоящего холодного старта выше. Проходящий прогон всё равно
  может залогировать более ранний `cmd1 timeout` перед `SD/MMC card found`, потому что
  драйвер повторяет попытки. Карта с валидным boot prefix в секторе 16 также заставляет
  BROM иногда загружаться с SD вместо сэмплирования FEL при холодном включении питания;
  вынимайте карту, когда нужен детерминированный вход в FEL.
- HIL падает с `missing a payload handoff`: задан `HIL_REQUIRE_HANDOFF=1`, но loader
  остался в своём цикле `S=0x`. Проверьте, что `payload.bin` присутствует и валиден, и что
  путь через карту прошёл успешно.
- `BOOT: boot.cfg: is N bytes, but the buffer holds 4095`: необязательный файл аргументов
  превышает окно в 4 KiB (включая завершающий NUL). Сократите его; loader отказывается
  делать handoff с обрезанными аргументами.
- HIL падает с `payload mismatch`: `payload.bin` на карте — не тот образ, с которым
  сравнивал HIL. Пересоберите через `cargo xtask payload` и скопируйте
  `target/rawboot-payload.img` поверх `payload.bin` на FAT-разделе либо передайте образ,
  который вы действительно записали, через `HIL_PAYLOAD_IMG`.
- Лог показывает `BOOT: handoff to ...`, но PD22 сохраняет ровное переключение loader
  каждые 50 мс: на карте старый payload. Пересоберите через `cargo xtask payload` и
  скопируйте `target/rawboot-payload.img` поверх `payload.bin` на FAT-разделе.
- HIL падает с `LED pattern not confirmed` или `HIL_REQUIRE_LED=1 needs an interactive
  prompt`: подтвердите коротко-длинную последовательность и повторите либо задайте
  `HIL_LED_CONFIRMED=1` после проверки платы.
- HIL падает с `payload image not found`: запустите `cargo xtask payload` или укажите
  `HIL_PAYLOAD_IMG` на образ, который вы записали на карту.
- HIL падает с `missing FEL: payload` при `HIL_FEL_PAYLOAD=1`: магия/адреса почтового
  ящика не дошли до loader, или loader старше этого пути. Пересоберите через
  `cargo xtask image` и сверьте значения `xfel write32` с таблицей почтового ящика.
- loader печатает `BOOT: FEL payload image ... is outside the SRAM staging window`: адрес
  или размер образа в почтовом ящике неверны, либо образ превышает окно в 44 KiB.
  Держите образ по `0x00039000` и пересоберите его через `cargo xtask payload`, если он
  вырос.
- HIL отклоняет `HIL_FEL_PAYLOAD=1` с `HIL_REQUIRE_SD`: путь FEL пропускает SD-карту;
  снимите `HIL_REQUIRE_SD` для прогона FEL.
- UART молчит: проверьте USART0 PE2/PE3, 115200 8N1 и что CH340 — это `/dev/ttyUSB0`.
- Лог начинается с повторяющихся строк `Hello`/`S=`: в буфере tty всё ещё остался
  предыдущий прогон, или плата в цикле сброса. Скрипт сливает буфер и теперь проваливает
  прогон при нескольких строках `Hello`; выполните цикл питания платы (не `xfel reset`) и
  повторите либо задайте `HIL_SKIP_PREFLIGHT=1`, чтобы слить и заменить работающий loader
  и игнорировать эти устаревшие строки.
- loader печатает `CLK: init timeout at ...`: какой-то PLL часов не захватился;
  захватите полную строку и адрес регистра для диагностики.
